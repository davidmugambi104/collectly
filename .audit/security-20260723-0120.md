## CRITICAL

### C-1. OAuth `state` is the raw `orgId` — no CSRF / no ownership check
- **Files:**
  - `src/app/api/quickbooks/connect/route.ts:5-9` (no auth, takes `?orgId=` and uses it as `state`)
  - `src/app/api/quickbooks/callback/route.ts:6-18` (treats `state` as the `orgId` to write tokens under)
  - `src/app/api/xero/connect/route.ts:5-16` / `src/app/api/xero/callback/route.ts:6-27`
  - `src/app/api/stripe-connect/connect/route.ts:5-19` / `src/app/api/stripe-connect/callback/route.ts:5-26`
  - `src/app/api/square/connect/route.ts:5-16` / `src/app/api/square/callback/route.ts:5-33` (PKCE adds defense-in-depth but `state` is still the orgId)
- **What:** Connect routes accept `?orgId=` from any unauthenticated requester, pass it as the OAuth `state` parameter, and the callback persists the resulting provider tokens under that same `orgId` with no check that the caller owns the org.
- **Why it matters:** Classic OAuth CSRF + account-takeover. An attacker who knows a victim orgId (visible in the dashboard URL, invoice numbers, etc.) can:
  1. Open `/api/quickbooks/connect?orgId=<victim>` → log into their own QBO when prompted.
  2. QBO redirects to the callback with the victim `orgId` as state.
  3. Attacker-controlled QBO account is now connected to the victim's org. Every sync, every invoice push, every customer pull now flows through the attacker's books.
  This silently swaps the org's accounting integration.
- **Fix:** Sign the state at connect-time (HMAC over `orgId + nonce + exp` using a server secret, or store a random `state → orgId + userId + exp` row in DB). On callback, look up the row, verify expiry, verify the user belongs to that org via `getAuth()`. Reject on mismatch.

### C-2. OAuth access/refresh tokens stored unencrypted at rest
- **File:** `src/db/schema.ts:136-137` — `integrations.accessToken`, `integrations.refreshToken` are plain `text`.
- **What:** All QBO, Xero, Square, Plaid, Stripe Connect refresh tokens are stored as plaintext in Postgres.
- **Why it matters:** A DB compromise (SQLi, backup leak, log dump, neon's accidental public snapshot) immediately yields full take-over of every connected accounting integration for every customer. Tokens have no expiry short enough to be self-healing.
- **Fix:** Encrypt at the column level with `pgcrypto` using a key from `INTEGRATIONS_ENC_KEY` (rotated). Or use a KMS-wrapped envelope. Never log or return these columns in API responses.

### C-3. Dev-auth shim has no `NODE_ENV` guard — accidental production exposure is catastrophic
- **File:** `src/middleware.ts:30` — `const hasClerk = !!(process.env.CLERK_SECRET_KEY && process.env.NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY) && process.env.USE_DEV_AUTH !== '1';`
- **File:** `src/lib/auth-helper.ts:16` — `if (process.env.USE_DEV_AUTH === '1') { return synthetic session }`
- **File:** `src/components/clerk-provider.tsx:18` — `if (process.env.NEXT_PUBLIC_USE_DEV_AUTH === '1' || ...)`
- **What:** The dev shim is gated only by `USE_DEV_AUTH !== '1'`. There is no `process.env.NODE_ENV === 'production'` cross-check anywhere.
- **Why it matters:** If `USE_DEV_AUTH=1` (or `NEXT_PUBLIC_USE_DEV_AUTH=1`) is ever set in the Vercel project dashboard for a quick local test, the entire middleware becomes a no-op and every API route that calls `getAuth()` returns the synthetic dev session. The dashboard, customer lists, invoices, integrations sync, webhooks (except signature-gated), everything is wide open. This is silent — no warning, no startup check.
- **Fix:** In `middleware.ts`, replace the gating with: `if (process.env.NODE_ENV === 'production' && process.env.USE_DEV_AUTH === '1') throw new Error('dev shim cannot be enabled in production');` and refuse to start. Same in `auth-helper.ts` and `clerk-provider.tsx`. Add a build-time check (e.g. a `prebuild` script that fails if both `NODE_ENV=production` and `USE_DEV_AUTH=1`).

## HIGH

### H-1. `/api/admin/interviews/*` placed in middleware's PUBLIC route list
- **File:** `src/middleware.ts:30` — `'/api/admin/interviews/(.*)'` is in `isPublicRoute`.
- **File:** `src/app/api/admin/interviews/export/route.ts:11-12` and `[id]/tag/route.ts:16-17` — they call `getAuth()` but no role check.
- **File:** `src/app/dashboard/admin/interviews/page.tsx:14-18` — page is at `/dashboard/admin/...` but only checks `if (!userId) redirect('/sign-in')`. No `role === 'admin'` check.
- **What:** "Admin" interview management is reachable by any signed-in user. The export returns ALL interview submissions across the system (no `orgId` filter — waitlist is global), including name, email, company, country, free-text pain point. A regular paying customer can grab the full lead list as CSV.
- **Why it matters:** Lead data is the core asset of the marketing site. This is a confidentiality breach of every interview respondent to any logged-in user.
- **Fix:** (a) Remove `/api/admin/interviews/(.*)` from the public matcher so middleware enforces auth. (b) Add an explicit role check inside the route/page (e.g. `if (membership.role !== 'owner' && membership.role !== 'admin') return 403`). (c) Audit what other routes under `/api/admin/*` may be added later.

### H-2. `getAuth()` shim has no Clerk fallback when dev shim is off
- **File:** `src/lib/auth-helper.ts:23` — `return await auth();`
- **Files using it directly:** All 14 routes that call `getAuth()` (verified).
- **What:** When `USE_DEV_AUTH !== '1'`, the helper defers to Clerk. But several routes that *should* also work in dev mode (e.g. `seed`, `events`) call Clerk's `auth()` directly instead of `getAuth()`. In dev shim mode those routes 500.
- **Why it matters:** Not a security hole, but it means dev shim mode is fragile. More importantly: if Clerk is ever temporarily misconfigured in production (key rotation, Clerk outage), these routes break silently and **defer to whatever the no-op `auth()` returns** — Clerk's `auth()` returns `null` for `userId` when not signed in, so they 401. But if there's any code path that returns a stale cached session, it could return data for a previous user. The pattern is inconsistent and a future contributor will likely just add another `await auth()` and re-introduce the issue. **Standardize on `getAuth()` everywhere.**
- **Fix:** Replace all `import { auth } from '@clerk/nextjs/server'` in `src/app/api/**/route.ts` with `getAuth()` from `@/lib/auth-helper`. Confirmed callers needing this: `src/app/api/seed/route.ts:9`, `src/app/api/events/route.ts:14,28`.

### H-3. `/api/upgrade-request` and `/api/integrations/sync` rely solely on middleware for auth
- **File:** `src/app/api/upgrade-request/route.ts:21-32` — no `getAuth()` call; takes `{orgId, plan, ...}` from body. Not in middleware public list, so protected only by `auth.protect()`.
- **File:** `src/app/api/integrations/sync/route.ts:30,71` — calls `getAuth()` ✓ but is in middleware public list (defense in depth issue, see L-2).
- **What:** `/api/upgrade-request` doesn't verify that the caller's `orgId` matches `data.orgId` in the body. A signed-in user (or in dev shim, anyone) can submit upgrade requests for any other org's `orgId`. The request records under that org and emails the founder.
- **Why it matters:** Trivially forgeable; in dev shim mode it's unauthenticated. The endpoint writes to the DB and triggers an external email.
- **Fix:** Add `const { orgId } = await getAuth(); if (!orgId || data.orgId !== orgId) return 401;` at the top of the handler. (Or remove `orgId` from the body entirely and use the session orgId.)

## MEDIUM

### M-1. In-memory rate limiter is per-instance, leaks memory, and won't run on serverless
- **File:** `src/lib/rate-limit.ts:5-9` — `const buckets = new Map<string, Entry>();`
- **What:** Buckets live in the Node process. On Vercel's serverless runtime every cold invocation gets a fresh Map, so the limiter is effectively disabled in production. Also no TTL cleanup — the map grows unbounded for the lifetime of a long-running instance.
- **Why it matters:** `waitlist`, `interview`, `lead-notify`, `payment/create-checkout`, `upgrade-request`, and `playbook/download` all rely on this for spam protection. On Vercel, they're unprotected. Memory leak matters only for the dev server but the same module is imported in production.
- **Fix:** Switch to Upstash (`@upstash/ratelimit`) — the `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` envs are already declared in `.env.example` but never wired up. Add a periodic cleanup for any in-process fallback.

### M-2. No `force-dynamic` / no cache headers on auth-aware GETs → risk of CDN cache poisoning
- **Files (all return per-`orgId` data):**
  - `src/app/api/exec-summary/route.ts` (in middleware public list, so unauthenticated calls hit it)
  - `src/app/api/forecast/route.ts` (same)
  - `src/app/api/invoices/route.ts`, `src/app/api/customers/route.ts`, `src/app/api/dunning/preview/route.ts`, `src/app/api/dunning/send/route.ts`, `src/app/api/sequences/[id]/route.ts`
- **What:** GETs that vary on `orgId` (via `getAuth()`) but lack `export const dynamic = 'force-dynamic'` and don't set `Cache-Control: private, no-store`. With Vercel's default ISR / CDN, two users' responses could be served from the same cached response (the first request to land gets cached, the second sees it).
- **Why it matters:** Cross-tenant data leak via the CDN.
- **Fix:** Add `export const dynamic = 'force-dynamic';` and `headers: { 'cache-control': 'private, no-store' }` on all routes that return per-`orgId` data. Or move them off the public matcher (so the `no-store` middleware can apply).

### M-3. `/api/waitlist` GET publicly returns last 10 emails
- **File:** `src/app/api/waitlist/route.ts:43-47`
- **What:** `GET /api/waitlist` (no auth, in middleware public list) returns the email addresses of the most recent 10 signups.
- **Why it matters:** PII leak. Marketing site visitor can enumerate signups.
- **Fix:** Either remove the GET handler entirely or change it to return `{ count: <number> }` only.

### M-4. `dunning/send` injects caller-supplied `body` into HTML without escaping
- **File:** `src/app/api/dunning/send/route.ts:47` — `html: \`<p style="white-space:pre-wrap;font-family:system-ui;">${data.body}</p>\``
- **File:** `src/app/api/dunning/test/route.ts:79` — same pattern.
- **What:** The dunning message body comes from a zod-validated string but is then concatenated into raw HTML and sent to the customer via Resend. No escaping.
- **Why it matters:** The route is auth-gated, so the attacker would be a malicious org admin or someone who has hijacked a session. Limited impact, but it's a stored-HTML-injection vector into customer inboxes, which can be used for phishing of payment links or to exfiltrate via injected `img` tags. Also: any customer who later replies sees the raw HTML in their inbox.
- **Fix:** Escape the body before interpolating, or pass the body as a text part and let the email client render it. Resend accepts `{ text, html }` separately.

### M-5. Dev-shim exposes `/api/integrations/sync` to anyone
- **File:** `src/middleware.ts:24` — `'/api/integrations/sync'` in public list.
- **What:** In dev shim mode, the middleware no-ops, so `getAuth()` returns the dev org and anyone who hits the endpoint can trigger a QBO/Xero sync against the dev org's connection. In prod this is fine (auth required) but in any dev-share / preview-deploy scenario this is a quiet exfil path for the dev org's data.
- **Why it matters:** Lower than C-1/C-3 but a real concern if a preview deployment is ever shared with a non-founder user.
- **Fix:** Remove `/api/integrations/sync` from the public matcher (it's a per-user action) and remove `/api/admin/interviews/(.*)` (see H-1). Re-evaluate every entry in `isPublicRoute` against "does an unauthenticated request need to land here?".

## LOW / INFO

### L-1. Stack traces leaked to client in many routes
- **Files:** All catch blocks return `String(e?.message ?? e)` in the response body — `quickbooks/callback`, `xero/callback`, `square/callback`, `stripe-connect/callback`, `plaid/connect`, `plaid/exchange`, `integrations/sync`, `dunning/test`, `dunning/send`, `cron/dunning`, `healthcheck`.
- **Why it matters:** Third-party SDK errors (QBO "invalid_client", Stripe "api_key_invalid", etc.) leak provider-internal context. Also useful for attackers to fingerprint.
- **Fix:** Log full error server-side with a request id, return `{ error: 'internal', requestId }` to client.

### L-2. `playbook/download` GET trusts email query param without zod
- **File:** `src/app/api/playbook/download/route.ts:48-58`
- **What:** `GET /api/playbook/download?email=anything` inserts `anything` (not validated) into waitlist. Trivially pollutes the lead list.
- **Fix:** Zod-validate the email or remove the GET path.

### L-3. Console logs include orgId / dispute id / charge id — useful for support, harmless
- **Files:** `src/lib/billing.ts:111,118,128,141,154,176,201,216,227,289,322` — all `console.warn('[stripe-webhook] ...')`.
- **Info:** Logs reference IDs not secrets. Fine to keep, but be aware Vercel's log retention may expose these. Consider redaction if you ever log full request bodies.

### L-4. `cors` / origin not enforced on POST routes
- **File:** `src/app/api/waitlist/route.ts`, `interview/route.ts`, `lead-notify/route.ts`, `playbook/download/route.ts` and the public-demo route all accept cross-origin POSTs (no `Origin` check, no `allowedOrigins` allowlist).
- **Why it matters:** Cross-site form submission is possible. Combined with no CSRF token, a malicious site can submit fake signups on behalf of the user. Impact is limited (data ends up in a waitlist) but it's a real abuse vector.
- **Fix:** Add a simple `if (req.headers.get('origin') && !ALLOWED.has(...)) return 403` or rely on same-origin cookies + a CSRF token. For the public lead forms specifically, consider switching to `application/x-www-form-urlencoded` with a server-issued nonce.

### L-5. No rate limit on AI endpoints
- **Files:** `src/app/api/dunning/preview/route.ts`, `src/app/api/exec-summary/route.ts`, `src/app/api/forecast/route.ts`, `src/app/api/dunning/test/route.ts`.
- **Why it matters:** Each call hits Gemini/OpenAI. In dev shim mode (or any signed-in user) you can burn your AI quota with a script.
- **Fix:** Add `rateLimit(getIp(req), { max: 20 })` or per-user.

### L-6. Stripe webhook error message echoes `e.message` to the response
- **File:** `src/app/api/webhooks/stripe/route.ts:15` — `error: \`webhook signature failed: ${e.message}\``
- **Why it matters:** Stripe SDK error messages are not sensitive but they reveal what the signature check expects.
- **Fix:** Return a generic `"invalid signature"` message.

### L-7. `events` route uses Clerk `auth()` directly, broken in dev shim
- **File:** `src/app/api/events/route.ts:14,28`
- **Fix:** Switch to `getAuth()`.

### L-8. `seed` route uses Clerk `auth()` directly, broken in dev shim
- **File:** `src/app/api/seed/route.ts:9`
- **Fix:** Switch to `getAuth()`.

### L-9. `npx tsc --noEmit` is not a security finding but: drizzle `sql\`\`` is parameterized, no raw user-supplied SQL anywhere
- **Files:** `src/app/api/healthcheck/route.ts:15` (literal `SELECT 1`); `src/app/dashboard/billing/page.tsx:55-56` (table name from string literal); all other `sql\`\`` usage is drizzle tagged template with column refs only.
- **Info:** Confirmed safe — drizzle's tagged template parameterizes interpolated values. No user input ever reaches raw SQL.

### L-10. No `eval`, no `child_process`, no `new Function` in `src/`
- **Info:** Confirmed via grep. Clean.

### L-11. `pay/[id]/page.tsx` exposes invoice + customer PII by ID (no auth, no rate limit)
- **File:** `src/app/pay/[id]/page.tsx` and `src/app/api/payment/create-checkout/route.ts`
- **What:** The public payment page (no auth) renders the invoice, customer name, and org name given the invoice id. The matching checkout endpoint creates a real Stripe session.
- **Why it matters:** Nanoid invoice IDs are unguessable, so this is by design. But there's no rate limit on the page itself (only on create-checkout). An attacker scraping the page won't get sensitive data beyond what the customer would see in a real pay link.
- **Fix:** Document the trust model. Optionally shorten TTL on the Stripe session and add per-IP throttling on the page render.

## ALREADY GOOD

- **Cron auth** (`src/app/api/cron/dunning/route.ts:9-15`) — bearer-token check + fail-closed when `CRON_SECRET` is unset. Textbook.
- **Stripe webhook signature verification** (`src/app/api/webhooks/stripe/route.ts:7-15`) — uses `constructEvent`, refuses on missing sig or secret.
- **Zod validation** — present on every POST/PUT that takes a body: `customers`, `invoices`, `dunning/send`, `dunning/test`, `dunning/preview`, `sequences/[id]`, `waitlist`, `interview`, `lead-notify`, `playbook/download`, `payment/create-checkout`, `upgrade-request`, `events`. No raw `await req.json()` followed by direct DB write.
- **Drizzle queries are all parameterized** — no `db.execute(sql\`...${userInput}...\`)`, no string concatenation. `sql\`\`` is only used for status enum comparisons and aggregate functions.
- **Public payment page (`/pay/[id]`) and customer checkout** use nanoid IDs (unguessable) and have IP-based rate limits.
- **Open-redirect search** — all `NextResponse.redirect` calls redirect to fixed internal paths (`/dashboard/integrations?...`) or to provider OAuth URLs (QBO/Xero/Square/Stripe Connect), not user input. No open-redirect.
- **No `eval`/`child_process`/`new Function`** in source.
- **No `console.log` of secrets** — no `process.env.X` in console statements, no token/key values logged.
- **Square uses PKCE** (S256) on top of the broken `state` — at least the token exchange is bound to the in-process verifier. (C-1 fix still required because `state=orgId` is the bigger hole.)
- **Dev-auth form** (`src/components/dev-auth-form.tsx`) is purely client-side; the actual session is server-issued via `getAuth()` reading the env. No fake JWT is generated client-side.
- **Production env (`.env.production`)** does not contain `USE_DEV_AUTH` or `NEXT_PUBLIC_USE_DEV_AUTH`, so the dev shim is correctly off in Vercel — assuming no one ever toggles it in the dashboard (see C-3).
- **No secrets committed to `.env.example`** — all values are empty placeholders.
