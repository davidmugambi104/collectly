## 5. DATA SAFETY

### Encryption at rest

**❌ No encryption.** OAuth tokens are stored as **plaintext** `text` columns:

```ts
// src/db/schema.ts (integrations)
accessToken: text('access_token'),
refreshToken: text('refresh_token'),
```

Anyone with read access to the prod DB (or a leaked dump) gets full QBO / Xero / Plaid / Square / Stripe account access for every connected org. There's also no `token_type` / `scopes` field.

**Customer email/phone are also plaintext** — this is normal for SaaS, but worth noting given you have `customerEmail` on `upgrade_requests` (Davie's contact info). At minimum, the *integration* tokens are the priority.

**Recommendation:** Use a KMS-backed column encryption (e.g. pgcrypto + app-side AES key from a secret), or at minimum swap the OAuth access/refresh tokens to an `encrypted_text` helper that uses a server-side key. Vercel KV / Upstash Redis can hold the encryption key separately. Even AES-GCM with a single key in an env var is better than plaintext for a defense-in-depth posture.

### Soft delete

**No `deletedAt` column on any table** — search for `deletedAt` / `deleted_at` returned zero hits in `src/db/`, `src/lib/`, and `src/app/`. The pattern is *consistently absent*, not inconsistently applied.

Cascade deletes via FKs handle org→children destruction. So this is intentional, not a bug. **No action required** unless you later need an "undo" or audit trail for deletions.

### PII

- Customer email + phone stored plaintext (typical for CRM-like apps).
- No DLP / row-level security configured — anyone with the DB connection string has full access.
- `memberships` correctly cascades on user delete (no orphaned memberships).

## 6. PERFORMANCE TRAPS

### N+1 in integration sync (HIGH IMPACT)

Both `quickbooks.ts` and `xero.ts` run a "fetch-then-upsert" loop where **each remote row triggers a separate `select` then `insert/update`**:

- `src/lib/integrations/quickbooks.ts:289-307` — for each QBO customer: 1 `select` (existence) + 1 `insert`/`update`. With `MAXRESULTS 1000` that's up to **2000 round-trips per sync**.
- Same pattern for invoices (lines 333-393).
- `xero.ts` mirrors this exactly (lines 270-385).

**Fix:** Bulk-fetch the existing rows for the org in one query keyed by `external_id`, then build a `Map` and do batched upserts. For PGlite/SQL, you can use `INSERT ... ON CONFLICT (org_id, external_id) DO UPDATE` once the missing index is added. Saves 1-2 orders of magnitude on sync time.

### Unbounded list queries (HIGH IMPACT in prod)

| File | Line | Query |
|---|---|---|
| `src/app/api/forecast/route.ts` | 29 | `db.select().from(customers).where(eq(customers.orgId, orgId))` — **no limit** |
| `src/lib/analytics.ts` | 122-127 | `paidRows` selects every paid invoice in last 90 days — no limit |
| `src/lib/dunning/scheduler.ts` | 26 | `db.select().from(dunningSequences).where(eq(isActive, true))` — bounded by # of orgs, low risk |
| `src/lib/dunning/scheduler.ts` | 38-46 | `overdueInvoices` selects every overdue invoice per sequence per org — no limit |

**Forecast route is the worst** — it dumps *every* customer record (with jsonb `payment_behavior`) over the wire on every forecast call. With 8 customers today it's fine; at 10k it'll OOM the serverless function.

**Fix:** Add `.limit(500)` to forecast's customer select (or aggregate in SQL with `SELECT id, payment_behavior FROM customers WHERE org_id = $1 LIMIT 500`); for analytics, compute `avgDaysToPay` server-side with `AVG()` + `FILTER`.

### Other findings

- **`src/lib/events.ts:73`** — silent bug:
  ```ts
  return db.select().from(events)
    .where(eq(events.orgId, orgId) && gte(events.createdAt, since));
  ```
  Uses JavaScript `&&` instead of `and()`. Result: the `gte` clause is *discarded*, and the second arg passed to `where` is a `Date` object (will be compared to orgId?). Likely crashes or returns all events. **Fix:** `and(eq(events.orgId, orgId), gte(events.createdAt, since))`.

- **`src/app/api/dunning/send/route.ts:38`** — **hard FK bug**:
  ```ts
  sequenceId: seq?.id ?? 'manual',
  ```
  `sequenceId` is `NOT NULL` and references `dunning_sequences.id` with cascade. If a user sends a manual dunning and has no active sequence, this inserts `sequenceId='manual'` which **fails the FK constraint** and returns 500. Either (a) make `sequenceId` nullable in the schema for manual sends, (b) auto-create a default sequence on first manual send, or (c) require an active sequence before allowing manual send.

- **`src/lib/integrations/quickbooks.ts:51`** — token refresh failure path:
  ```ts
  await db.update(integrations).set({ status: 'error', updatedAt: new Date() }).where(eq(integrations.id, integ.id));
  ```
  If the access token is invalid for *one* API call, the integration gets marked `error` permanently. There's no auto-retry on the next call. Combined with plaintext tokens, a leaked token means a permanent DoS on the integration until Davie manually resets it.

## 7. TRANSACTION USAGE

**Zero transactions found** in `src/`. (`grep -r "db.transaction" src/` → empty.)

This is the highest-priority issue. Multi-step operations currently at risk:

| File | Lines | Operation | Failure mode if step 2 fails |
|---|---|---|---|
| `src/app/api/invoices/mark-paid/route.ts` | 22-25 | insert payment → update invoice | Phantom payment row; invoice still shows unpaid |
| `src/lib/billing.ts:255-269` | insert payment → update invoice (mark paid) | Same — Stripe webhook replay could double-count or leave invoice stale |
| `src/lib/billing.ts:271-275` | update invoice → recordEvent | Event audit log could be missing for a real payment |
| `src/lib/integrations/quickbooks.ts:294-307` | check existing customer → insert/update | Two concurrent syncs could both insert the same customer (race) — though the `(org_id, external_id)` index would prevent a true duplicate, you'd waste a write |
| `src/lib/dunning/scheduler.ts:71-130` | insert run → send email → update run status → record event | Email sent but run left as `scheduled` on crash; or `failed` recorded but customer never got it |
| `src/app/api/dunning/send/route.ts:42-48` | insert run → send → update run + invoice | Half-applied state on send failure |

**Fix:** Wrap each in `db.transaction(async (tx) => { ... })`. Drizzle supports this natively. The two Stripe webhook paths (`markInvoicePaidFromCheckout`, `markInvoicePaidFromPaymentIntent`) are the most critical because Stripe **replays webhooks** — a non-idempotent insert+update is a money-correctness issue.

There's also a TOCTOU race in `markInvoicePaidInDb`: it reads `inv.amountPaid`, then another concurrent payment could write first, and you'd overwrite the new value. The `existingPayment` check is also not atomic with the insert.

## 8. ACTIONABLE FIXES (priority order)

### 🔴 P0 — Correctness / money-safety

1. **Wrap payment + invoice updates in `db.transaction`** (`src/lib/billing.ts:255-269`, `src/app/api/invoices/mark-paid/route.ts:22-25`). Also make them truly idempotent — `existingPayment` check is non-atomic with the insert.
2. **Fix the FK bug** in `src/app/api/dunning/send/route.ts:38`. Either make `sequenceId` nullable, or auto-create a default sequence, or require an active one before allowing manual send.
3. **Fix the `lib/events.ts:73` query** — replace `eq(...) && gte(...)` with `and(eq(...), gte(...))`.

### 🟠 P1 — Security

4. **Encrypt integration tokens at rest** (`integrations.access_token`, `integrations.refresh_token`). Use AES-GCM with a key from Vercel KV / env var. At minimum, mark the columns as sensitive and restrict prod read access.
5. **Document PII handling** for `customerEmail`, `customerPhone`, `customerName` — even if you keep plaintext, the DB dump backup posture should be reviewed.

### 🟡 P2 — Performance

6. **Add the missing indexes** (§2 above). Top 5 are high-leverage:
   - `invoices (org_id, external_id)` — unblocks the bulk-upsert fix
   - `payments (customer_id)` — fixes customer-page latency at scale
   - `payments (paid_at)` — fixes analytics month-bucketing
   - `events (org_id, created_at DESC)` — fixes dashboard event log
   - `dunning_sequences (org_id, is_active)` — fixes every dunning page
7. **Add `.limit()` to unbounded queries** in `forecast/route.ts:29` and `analytics.ts:122-127` (compute aggregates in SQL).
8. **Replace N+1 sync loops** in `quickbooks.ts` and `xero.ts` with batched upsert (`INSERT ... ON CONFLICT`).

### 🟢 P3 — Housekeeping

9. **Add `memberships.updated_at`** for consistency.
10. **Decide on soft-delete** — currently absent everywhere; document the choice (cascade on org delete is fine for a B2B tool).
11. **Generate a new migration** that includes all P2 indexes so prod gets them.
12. **Consider a `delete_audit` table** if you ever need to answer "did org X ever exist?" — `organizations` is hard-deleted today.
