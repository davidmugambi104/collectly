## RUNTIME ERRORS — 🔴 2 active issues on prod

Pulled from Vercel logs for `dpl_8vf5mApJTcWopZwTKqDQR3ghrq8x` (last hour, latest 100 lines):

### 1. `/api/lead-notify` — ZodError: missing `type` field (multiple occurrences)
```
Error [ZodError]: [{
  "expected": "'waitlist' | 'interview' | 'dunning_test'",
  "received": "undefined",
  "code": "invalid_type",
  "path": ["type"],
  "message": "Required"
}] at src/app/api/lead-notify/route.ts:24
```
The route's Zod schema makes `type` required, but at least one client is POSTing without it. The catch block in the route returns `ok: true` to the client but logs the error, so **user submissions appear to succeed while lead notifications silently fail** — leads are being lost.

### 2. `/api/lead-notify` — Resend `from` field validation error
```
Lead notify failed: resend: validation_error:
Invalid `from` field. The email address needs to follow the
`email@example.com` or `Name <email@example.com>` format.
```
The current `from` string is built in `src/lib/infra.ts:32`:
```ts
from: opts.from ?? `${process.env.RESEND_FROM_NAME ?? 'Collectly'} <${process.env.RESEND_FROM_EMAIL ?? 'hello@getcollectly.app'}>`
```
So one of `RESEND_FROM_NAME` or `RESEND_FROM_EMAIL` is set to a value Resend rejects (likely the env var contains a stray character, an unescaped `<`/`>`, or the from name has no value producing ` <>email>`).

**Together these two errors are the same root cause in different forms:** the ZodError path throws before sending, but even successful parses hit the Resend error — so **all lead notifications on prod are silently failing**.

## ACTIONABLE FIXES (priority order)

### 🔴 P0 — Stop losing leads
1. **Fix Resend `from` field.** Inspect `RESEND_FROM_NAME` and `RESEND_FROM_EMAIL` in Vercel project env. The most likely culprit: an empty/null value combined with the default `Collectly <>` becoming ` <>email>`. Either set both env vars explicitly to validated values, or strip the name interpolation when `RESEND_FROM_NAME` is unset. Add a unit test (which doesn't exist yet) that asserts `from` matches Resend's regex.

### 🔴 P0 — Lead-notify silently swallows errors
2. The route returns `ok: true` to the client even when the email send throws. Change this: only return `ok:true, sent:true` when the Resend call succeeds, and return `ok:false, code:'NOTIFY_FAILED'` (still 200 to keep client UX) when the Zod parse or send fails. Add a `console.error`/PostHog capture so failures show up in monitoring. **Right now you cannot tell from the client that the lead was lost.**

### 🟡 P1 — Add tests (currently zero)
3. Add **vitest** (lighter than jest, plays well with Next 15) and write at minimum:
   - `src/app/api/lead-notify/route.test.ts` — covers all three `type` values, missing fields, and Resend failure paths
   - `src/app/api/invoices/route.test.ts` — CRUD on invoices
   - `src/app/api/cron/dunning/route.test.ts` — cron auth + behavior
   - `src/lib/infra.test.ts` — `sendEmail` `from` field construction (would have caught bug #1)
4. Wire `npm test` and add to a pre-deploy hook.

### 🟡 P1 — Migrate `next lint`
5. Run the codemod: `npx @next/codemod@canary next-lint-to-eslint-cli .` (interactive). Without this, lint is a no-op in Next 16.

### 🟢 P2 — Tighten `next.config.mjs`
6. Replace `hostname: '**'` in `images.remotePatterns` with an explicit allowlist (Clerk, Stripe, Resend, any image hosts you actually use).

### 🟢 P2 — Misc warnings
7. The webpack `big strings` warning during build is from pglite; can be silenced by switching to Buffer-based serialization, but it's not blocking.
