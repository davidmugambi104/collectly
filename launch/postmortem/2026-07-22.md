## 3. What Didn't Work (agent observations + placeholders)

- **The "GPT-4o" stale copy in `/features` and `/dashboard/dunning` page was
  still live at launch**. We're using Gemini, not GPT-4o. A technical buyer
  reading the homepage would notice the mismatch. **Fix shipped 2026-07-23**
  in audit follow-up (4 spots: features, dashboard, homepage, public-demo
  comment). **Why it failed**: copy was written when we were considering
  OpenAI, never updated after switching to Gemini in the integration audit
  on 2026-07-23.

- **The dev auth shim (`USE_DEV_AUTH=1`) had no `NODE_ENV` guard**. If
  someone ever set this in the Vercel dashboard "to test something", the
  entire middleware becomes a no-op and every authenticated route returns
  the synthetic dev session. **Fix shipped 2026-07-23** in
  `src/middleware.ts` and `src/lib/auth-helper.ts` — both now throw at
  module load if `NODE_ENV === 'production' && USE_DEV_AUTH === '1'`.
  **Why it failed**: guard added in v1 for dev convenience, never hardened
  for production deploy risk.

- **OAuth state parameter was the raw `orgId`** with no signature or
  ownership check (QBO, Xero, Square, Plaid, Stripe Connect). An attacker
  who knew a victim orgId could trigger a token-swap attack. **Status**:
  **NOT YET FIXED** as of 2026-07-23. High-priority item on the progressive
  plan. Need HMAC-signed state or DB-backed `state → orgId + userId + exp`
  lookup. **Why it failed**: same dev-shim pattern of "this is just a
  prototype" hardening gap.

- **Two real P0 DB bugs in the dunning code path were live at launch**:
  (1) `getEventsByType` used JS `&&` instead of drizzle's `and()`, silently
  dropping the type and time-window filters; (2) `api/dunning/send` would
  500 on first manual dunning send because `sequenceId: 'manual'` violated
  the FK to `dunning_sequences.id`. **Both fixed 2026-07-23**. **Why they
  failed**: the manual-send path was a "demo" endpoint that never got an
  end-to-end test, and the events.ts function had no callers so the bug
  never surfaced.

## 4. The Surprises

- **Production had 0 Stripe webhook endpoints registered** until the
  2026-07-23 integration audit. Stripe webhooks would have silently dropped
  every event if a customer had paid through the portal. **Was it good
  or bad?**: Bad — but caught early because no real customers yet.
  **Recovered**: yes, `we_1Tw85JJlrsJQtG43bmCya4as` registered pointing
  at `/api/webhooks/stripe` with 9 events.

- **Resend FROM email was `davidmugambi104@gmail.com`** at launch — a
  Gmail address that Resend would reject on the first real send. Was
  flagged in the integration audit and fixed. **Why surprising**: the
  `.env.example` had `hello@getcollectly.app` as the default, but the
  Vercel production env had been populated with the gmail address and
  never validated against the verified `getcollectly.app` domain.

## 7. The 3 Things to Do DIFFERENTLY Next Time

> Pre-filled with items the agent observed, but Davie should validate.

1. **End-to-end test every API path before launch day, including the
   "manual" / "demo" endpoints** that look like dev-only. The
   `api/dunning/send` route was clearly marked as a manual one-off but
   had a FK bug that would have 500'd the first time anyone used it.

2. **Run a security audit at least 48h before launch, not after**. The
   `src/middleware.ts` dev-shim, OAuth state plaintext, and token
   plaintext-at-rest all should have been caught pre-launch. They're
   not catastrophic if no real customer hits them yet, but they are
   catastrophic if they do.

3. **Diff `.env.example` against actual Vercel production env at deploy
   time**. The `RESEND_FROM_EMAIL`, `STRIPE_WEBHOOK_SECRET`, and stale
   QBO/Stripe values were all just typos/copy-paste errors that
   verification would have caught in 5 min.

## 8. The 3 Things to KEEP Doing

1. **Living `.audit/` directory with dated reports** — the parallel
   sub-agent audit pattern (7 agents covering security, code, build, prod
   health, DB, outreach, UX in ~10 min each) found 12+ real P0/P1 issues
   in one pass. Cheaper than a 2-day manual review.

2. **Outreach template versioning with reply-rate rubrics** — `t1-cold-v2.md`
   has a 0/10→4+/10 reply-rate scale built into the file. That kind of
   explicit measurement-loop is good. Keep it.

3. **The progressive-plan-in-MEMORY pattern** — committing what was fixed
   in each session to `memory/YYYY-MM-DD.md` (or session-specific files)
   makes the next session's start-up trivial. Don't stop.
